## 2. Findings

### [Medium] Strict panel ID matching in layout validation rejects saved workspaces on plugin catalog changes (Plausible Risk — Carried Over)

- **Reference:** [`src/layout/layoutPersistence.ts` L31-L36](file:///c:/projects/grammar-lab/dash-lab/src/layout/layoutPersistence.ts#L31-L36)
- **Context:**
  ```typescript
  const expected = new Set(panels.map((panel) => panel.id));
  const definitions = value.panels;

  if (Object.keys(definitions).length !== expected.size || Object.keys(definitions).some((id) => !expected.has(id))) {
    throw new Error('Saved layout is incompatible with the current panels.');
  }
  ```
- **Why it matters:** Unlike plugin _state_ (which now gracefully ignores unknown participants and preserves missing entries per ADR-003), Dockview _layout_ validation remains strictly bijective. If an application updates its plugin set (adding or removing a panel), `useLayoutManagement` encounters this error on startup and falls back to the default arrangement, discarding the user's customized layout.
- **Suggested Improvement:** Reconcile layout checkpoints gracefully upon startup: drop definitions for removed panels and dock newly added panels into default or active groups rather than rejecting the entire saved layout.
